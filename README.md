# Codebase Q&A Agent

A local, zero-cost AI agent that answers questions about your codebase using RAG (Retrieval-Augmented Generation) and tool-calling — no API keys, no cloud costs, runs entirely on your machine.

## What it does

Point it at any code repo, and it:
- Ingests and chunks the codebase, storing embeddings in a local vector database
- Answers natural-language questions about the code using retrieved context
- Decides which tool to use based on the question — semantic search, exact keyword search, or file listing

## Stack

- **LLM**: [Ollama](https://ollama.com) running `qwen2.5-coder:1.5b` (fully local, free)
- **Embeddings**: `sentence-transformers` (`all-MiniLM-L6-v2`, local, free)
- **Vector store**: [ChromaDB](https://www.trychroma.com/) (local, free)

## How it works

1. `ingest.py` — walks the target repo, chunks each file (50 lines per chunk), generates embeddings, and stores everything in ChromaDB. It also builds a special "project structure overview" chunk so structural questions have real data to retrieve from.
2. `agent.py` — the main agent loop:
   - Takes a question
   - Asks the model to pick a tool: `search_codebase` (semantic search), `grep_exact` (exact keyword match), or `list_files` (structure listing)
   - Runs the chosen tool, retrieves relevant context
   - Feeds the context + question back to the model to generate a final answer
3. `query.py` — a simpler version without tool-calling, kept for comparison (pure RAG, no routing).

## Setup

```bash
# 1. Install Ollama and pull the model
ollama pull qwen2.5-coder:1.5b

# 2. Install Python dependencies
pip install -r requirements.txt

# 3. Set REPO_PATH in ingest.py and agent.py to point at the codebase you want to query

# 4. Ingest the codebase
python ingest.py

# 5. Start asking questions
python agent.py
```

## What I learned building this

The first version hallucinated folder names that didn't exist in the actual repo (`services/`, `hooks/`, `tests/`, etc. — none of which were real) when asked about project structure. The cause: the vector store had no chunk that actually described the repo's structure, so the small local model filled the gap with folder names it had seen in other Next.js projects during training.

Fix: added a dedicated "project structure overview" chunk during ingestion, generated by walking the actual repo tree. This gave retrieval something real to return, which eliminated the hallucination (though the model still occasionally miscategorizes files vs. folders — a known limitation of small local models).

## Known limitations

- `qwen2.5-coder:1.5b` is a small model — tool-routing occasionally fails and falls back to semantic search
- **Follow-up questions with pronouns ("which file handles that?") are unreliable.** Initially, the tool router had no access to conversation history, so it searched for the literal word "that" and returned a confidently wrong file. After passing history into the router with an explicit instruction to resolve pronouns, the model's behavior improved from *confidently wrong* to *honestly uncertain* (it now says "I need more context" instead of guessing) — but it still can't reliably turn "that" into the right concrete search term. This appears to be a genuine capacity limit of a 1.5B parameter model doing multi-step reasoning (resolve pronoun → form search query), not a prompting bug. A larger model (7B+, or a hosted model like Claude/GPT) would likely handle this correctly.
- Chunking is line-based, not AST-aware, so chunks can split functions awkwardly
